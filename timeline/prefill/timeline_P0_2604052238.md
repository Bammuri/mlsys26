# Prefill Timeline — P0 — 2604052238

## Stage Summary

이 문서는 **GDN Prefill P0 단계**를 기록한다.

P0의 의미:

- native CUDA prefill baseline을 만들고
- 실행 가능성을 증명하고
- 이후 최적화의 출발점을 고정하는 단계

현재 baseline 상태:

- definition: `gdn_prefill_qk4_v8_d128_k_last`
- config language: `cuda`
- entrypoint: `binding.cpp::run`
- binding: `torch`
- core kernel: `solution/cuda/kernel.cu`

---

## Why this stage exists

prefill은 decode와 다르게:

1. varlen `cu_seqlens`를 처리해야 하고
2. recurrent state carry가 있고
3. 긴 sequence 구간에서 병목이 커지고
4. official prefill proxy가 `warmup_runs=1`, `iterations=5`, `num_trials=3`로 비교적 무겁다 (`background.md:31-32`)

그래서 먼저 해야 할 일은

> “가장 빠른 최종 최적화”가 아니라  
> “실제로 돌아가고, 정확하고, native CUDA path로 이어지는 기준선”을 확보하는 것

이었다.

---

## Why we optimized / structured it this way in P0

### 1. Prefill을 먼저 잡은 이유

- 현재 main definition이 prefill이었다
- prefill이 decode보다 더 넓은 algorithmic surface를 갖는다
  - varlen
  - recurrent update
  - state writeback
  - long-context pressure
- prefill이 통과하면 decode보다 더 많은 공통 수학적 요소를 검증할 수 있다

즉,

> prefill을 먼저 잡는 게 전체 GDN 구현의 기반을 만드는 데 유리했다

### 2. 처음부터 native CUDA까지 간 이유

처음 bring-up 단계에서는 Python wrapper도 썼지만,
P0를 확정할 때는 **실제 native CUDA path**로 옮겼다.

이유:

1. 최종 목표가 `kernel.cu` 최적화이기 때문
2. Python wrapper baseline은 correctness 확인에는 유용하지만,
   실제 contest용 CUDA baseline이라고 보기는 약했기 때문
3. background가 명확히 C++/CUDA 중심 Blackwell 최적화를 요구하기 때문 (`background.md:36-43`)

즉,

> P0 baseline은 “실제로 `kernel.cu`가 돈다”는 사실을 증명해야 했다

### 3. Torch binding을 선택한 이유

P0 단계에서는 `tvm-ffi`보다 **Torch extension binding**이 더 빠른 bring-up 경로였다.

이유:

1. `binding.cpp + kernel.cu` 구조로 바로 native symbol을 연결할 수 있음
2. compile error surface를 빠르게 확인할 수 있음
3. starter harness 안에서 native CUDA path를 여는 가장 짧은 경로였음

즉,

> P0에서는 “최적의 최종 binding”보다 “실제로 native CUDA를 켜는 shortest path”가 더 중요했다

### 4. Quick mode를 먼저 만든 이유

full official run은 bring-up 단계에서 너무 무겁다.

이유:

1. dataset이 100 workloads
2. prefill official-style config가 상대적으로 무거움
3. native compile/image/toolchain 문제를 먼저 잡아야 했음

그래서 quick mode를 만들었다:

- `warmup_runs=1`
- `iterations=1`
- `num_trials=1`
- `use_isolated_runner=False`

이 방식은

> “컴파일이 되느냐 / correctness가 맞느냐 / subset에서 바로 PASS 하느냐”

를 가장 빨리 확인하게 해줬다.

### 5. 왜 shared-memory heavy correctness-first kernel로 시작했는가

현재 `kernel.cu`는 `(sequence, v-head)` 단위 CTA에서
fp32 state tile 전체를 shared memory에 올린다.

이 구조를 P0에서 택한 이유:

1. k-last state semantics를 명확히 유지하기 쉽다
2. reference recurrence를 native CUDA로 옮기기 쉽다
3. correctness debugging이 쉽다
4. 나중에 occupancy 문제를 드러내더라도, baseline으로서 의미는 충분하다

즉,

> P0에서는 “가장 빠른 구조”보다 “가장 명확하게 맞는 구조”를 택했다

## What got solved in P0

### A. Dataset / runner path

- active dataset을 `mlsys26-contest`로 고정
- Modal volume/mount path 정리
- quick subset execution path 확보

### B. Native build path

- `config.toml`을 native CUDA spec으로 정리
- `binding.cpp::run` export 연결
- `kernel.cu` native compute path 연결
- Modal CUDA devel image + `CUDA_HOME` 설정으로 Torch extension compile 가능화

### C. Benchmark proof

P0 proof:

- 1 workload quick PASS
- 5 workloads quick PASS

대표 결과:

- `Workload 77daf91d...: PASSED | 0.114 ms | 12.81x speedup | abs_err=5.96e-08, rel_err=9.53e-03`
- 5 workloads quick 평균:
  - avg latency: `0.386 ms`
  - avg speedup: `13.51x`

즉,

> P0는 “native CUDA prefill baseline exists and is real”을 증명했다

---

## What P0 deliberately did NOT optimize yet

P0에서는 일부러 다음을 미뤘다:

1. long-sequence specialized scheduling
2. CTA/warp mapping 재설계
3. vectorized K-dim aggressive optimization
4. CUDA Tile / Blackwell-specific deeper primitive 적용
5. 100 workload official-style full pass

이유:

> baseline이 없으면 최적화는 의미가 없기 때문

---

## Risks left after P0

1. 현재 커널은 shared-memory footprint가 큼
2. long-seq tail 최적화는 아직 없음
3. official-style full 100 workload run은 아직 미검증
4. B200-specific 최적화는 거의 아직 시작 전

---

## Exit criteria for P0

P0는 다음 조건을 만족했기 때문에 종료로 본다:

1. native CUDA compile path가 Modal B200에서 실제로 동작
2. quick subset correctness pass 확보
3. benchmark output/log path가 usable
4. 이후 단계(P1+)에서 성능 최적화를 시작할 수 있는 baseline 확보
