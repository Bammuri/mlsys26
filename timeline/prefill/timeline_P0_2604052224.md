# GDN Prefill Baseline Timeline

## TL;DR

현재 baseline은 **native CUDA baseline**이다.

- track: `gdn_prefill_qk4_v8_d128_k_last`
- config language: `cuda`
- entrypoint: `binding.cpp::run`
- binding: `torch`
- core implementation: `solution/cuda/kernel.cu`
- current verified status:
  - Modal B200에서 **native CUDA path compile + run + PASS**
  - quick subset 5 workloads 기준 **PASSED=5/5**

이전의 Python wrapper baseline은 bring-up 단계였고, 현재는 그 위에서 실제 `kernel.cu`가 실행되는 native path까지 연결한 상태다.

이 방식의 목적:

1. contest harness를 빨리 통과

이 단계는 bring-up baseline으로 유효했고, subset workload에서 PASS를 확인했다.

하지만 이것은 어디까지나 **intermediate baseline**이었다.

그래서 아래 기능을 추가했다:

- `warmup_runs=1`

관련 코드:

## 5. Native CUDA baseline design

이후 구조를 다시 CUDA 중심으로 정리했다.

### 5.1 Config

현재 config:

- `language = "cuda"` (`config.toml:7`)
- `entry_point = "binding.cpp::run"` (`config.toml:8`)
- `binding = "torch"` (`config.toml:11`)

즉, 이제 benchmark harness는 Python module이 아니라
**Torch CUDA extension builder**를 사용한다.

### 5.2 Native binding

추가 파일:

- `solution/cuda/binding.cpp`

역할:

- `run(...)` exported symbol 제공
- Python/benchmark 쪽 signature와 native CUDA 함수를 연결

관련 코드:

- `solution/cuda/binding.cpp:5-33`

### 5.3 Native kernel

핵심 구현:

- `solution/cuda/kernel.cu`

현재 커널 특징:

1. GDN prefill 전용
2. 고정 shape 가정
   - `q heads = 4`
   - `k heads = 4`
   - `v heads = 8`
   - `head_size = 128`
3. `cu_seqlens` 기반 varlen prefill
4. input: bf16 / state: fp32 / output: bf16
5. state layout: k-last `[N, H, V, K]`

관련 코드:

- constants: `solution/cuda/kernel.cu:14-18`
- kernel body: `solution/cuda/kernel.cu:42-124`
- exported native entry: `solution/cuda/kernel.cu:128-240`

현재 구현은 correctness-first이며, aggressive Blackwell tuning은 아직 아니다.

## 7. Why native build initially failed

native CUDA path로 전환한 직후, 첫 compile은 실패했다.

원인:

- Modal image에서 `CUDA_HOME`이 없었음
- Torch extension build가 CUDA toolchain을 찾지 못함

실제 에러:

- `CUDA_HOME environment variable is not set`

해결:

- Modal image를 CUDA devel base image로 변경
- `CUDA_HOME=/usr/local/cuda` 설정

관련 코드:

- `scripts/run_modal.py:35-39`

현재 image:

- `nvidia/cuda:13.0.2-devel-ubuntu24.04`

## 10. Design choices and rationale

### Why prefill first?

- 현재 config/plan 중심이 prefill
- GDN prefill이 decode보다 더 많은 algorithmic surface를 포함
- varlen + state carry + recurrent update까지 한 번에 검증 가능

### Why quick subset mode first?

- official run은 너무 무거움
- build/JIT/toolchain 문제를 빠르게 발견하려면 subset이 훨씬 효율적

### Why Torch binding for native baseline?

- starter harness 안에서 가장 짧게 native CUDA path를 여는 방법
- TVM-FFI보다 bring-up 속도가 빠름
- `binding.cpp + kernel.cu` 구조로 native compile 확인이 쉬움

### Why keep CUDA-centric repo structure?

- 사용자가 명시적으로 `solution/cuda/binding.py` / CUDA 중심 구성을 선호
- 최종 목표가 native CUDA 최적화이기 때문

## 11. Remaining risks

1. **Kernel structure is still naive**
   - 현재는 correctness-first
   - long-seq, register reuse, shared tiling 최적화 여지가 큼

2. **Shared memory footprint**
   - 현재 per-(seq, head) 128x128 fp32 state shared memory 사용
   - occupancy 관점에서 더 좋은 타일링이 필요할 수 있음

3. **No full official pass yet**
   - 100 workloads 전체
   - official-style iterations/trials
   - 아직 실행 전

4. **Background directives are only partially exploited**
   - `d128`, `k_last` 고정은 사용
   - 하지만 Blackwell-specific CUDA Tile / deeper fusion / NUMA-aware host strategy는 아직 미반영
